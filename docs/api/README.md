# Integration API

Версионированный HTTP API для внешних клиентов (боты, сервисы напоминаний и аналогичные интеграции). Источник данных тот же, что у публичного сайта: live-расписание университета с ограниченным кэшем в памяти.

**Контракт API** (единственный канонический): этот README + машиночитаемый [OpenAPI 3.1](openapi.json). Отдельный «бумажный» договор на поля ответа не ведётся: изменения схемы фиксируются обновлением этих двух файлов в репозитории.

Публичные маршруты сайта (`/api/groups`, `/api/schedule` и др.) этим документом не описываются. Идентификатор группы для запросов ниже берётся из публичного `GET /api/groups`.

## Роли

| Роль | Кто | Ответственность |
| --- | --- | --- |
| **Оператор API** | Хостинг Misisync | Endpoint `:8443`, HTTPS домена, доверенный `ca.crt` на gateway, секрет канала nginx→backend |
| **Партнёр (клиент)** | Владелец бота | Свой CA, выпуск `client.key` / `client.crt` для бота, подписки и напоминания |

Модель доступа: **партнёр владеет CA**. Оператор не подписывает клиентские сертификаты и не хранит `ca.key` партнёра. На VPS оператора лежит только публичный `ca.crt`, которым gateway проверяет предъявленные клиентские сертификаты.

## Endpoint

| | |
| --- | --- |
| Method | `GET` |
| Path | `/api/v1/schedule` |
| Base URL (production) | `https://schedule.sovngarde.ru:8443` |
| Auth | mTLS: клиентский сертификат, выпущенный CA партнёра (этот CA зарегистрирован на gateway) |
| TLS server | сертификат домена (Let's Encrypt); проверку серверного сертификата отключать не требуется |

Пример (на стороне партнёра):

```sh
curl --cert client.crt --key client.key --get \
  --data-urlencode 'group_id=МПИ-26-1-1' \
  --data-urlencode 'start=2026-09-07' \
  --data-urlencode 'end=2026-09-13' \
  --data-urlencode 'limit=50' \
  'https://schedule.sovngarde.ru:8443/api/v1/schedule'
```

`group_id` совпадает с полем `id` (и обычно с `name`) из `GET /api/groups` — это имя группы, не внутренний числовой id университета.

Gateway принимает только этот path и только `GET`. Остальные пути на порту 8443 отвечают `404`. Заголовок `X-Integration-Key` выставляет сам gateway; передача его из браузера или произвольного клиента доступа не даёт: публичный Next.js-прокси маршрут `/api/v1` не проксирует.

## Параметры запроса

| Параметр | Обязательный | Описание |
| --- | --- | --- |
| `group_id` | да | Имя группы (`id` из `/api/groups`) |
| `start`, `end` | да | Границы диапазона дат, включительно; не более 31 дня; `end` ≥ `start` |
| `subgroup` | нет | Оставить занятия выбранной подгруппы и занятия без уточнения подгруппы |
| `limit` | нет | Размер страницы, 1–100 (по умолчанию 50) |
| `offset` | нет | Смещение, 0–10000 |
| `snapshot` | со 2-й страницы | Значение `snapshot` из первого ответа |

Сортировка занятий: дата, время начала, идентификатор. Время в ответе — `Europe/Moscow` (`timezone` в теле). Если время неизвестно, поле остаётся `null`: клиент не должен подставлять вымышленный слот для напоминаний.

Пустая подгруппа в источнике не означает «занятие для всей группы» — это неопределённость upstream. Фильтр `subgroup` сохраняет такие записи вместе с явно выбранной подгруппой.

## Пагинация и согласованность

- `total` — число занятий после фильтра.
- `next_offset` — следующий `offset`, либо `null` в конце выборки.
- `snapshot` — контрольная сумма данных и параметров запроса.

Начиная со второй страницы передавайте `snapshot` первого ответа. Если данные или параметры изменились, API отвечает `409`: запросите первую страницу заново. Это проверка согласованности среза, а не серверная сессия пагинации.

## Семантика ответа

| Поле / признак | Смысл |
| --- | --- |
| `lessons` | Календарные занятия выбранного окна |
| `fetched_at`, `stale`, `warnings`, `available_dates` | Состояние и оговорки источника |
| `academic_weeks` | Оценка верхней/нижней недели для каждой календарной недели диапазона |

`academic_weeks` не меняет набор занятий. Поля `kind=upper|lower`, `estimated=true`, опора и пояснение. Опора задаётся на сервере (`ACADEMIC_REFERENCE_DATE`, `ACADEMIC_REFERENCE_KIND`) и отражает подтверждённую конфигурацию сервиса, а не официальное поле API университета.

Пустой список занятий не заменяет ошибку загрузки. При `502` / `503` нельзя интерпретировать ответ как отмену ранее известных пар и снимать уже запланированные напоминания.

## Ответственность клиента

Интеграционный API предоставляет срез расписания. Подписки получателей, планировщик уведомлений, выбор опережения («за N минут») и дедупликация отправок реализуются на стороне клиента.

Идентификатор занятия сам по себе недостаточен как ключ напоминания: учитывайте дату, время, получателя и при необходимости предмет. При `start_time = null` напоминание по часам не строится.

## Ошибки и лимиты

| Код | Условие |
| --- | --- |
| `403` | Нет действительного клиентского сертификата / отказ аутентификации канала |
| `404` | Неизвестная группа |
| `409` | `snapshot` не совпал — перезапустите пагинацию |
| `422` | Некорректные параметры (в т.ч. диапазон > 31 дня, `snapshot` без первой страницы) |
| `429` | Лимит gateway |
| `502` | Upstream недоступен |
| `503` | Upstream занят; есть `Retry-After` |

Лимит gateway: 30 запросов в минуту на серийный номер клиентского сертификата, burst 5. mTLS не защищает от исчерпания сетевой ёмкости. Общие лимиты concurrency и кэша backend остаются в силе для всех потребителей источника.

## Выпуск доступа

Интеграционный вход по умолчанию выключен (`INTEGRATION_ENABLED=false`). Не включайте его до действующего HTTPS домена и полученного от партнёра `ca.crt`. Сборка develop не активирует production-gateway автоматически.

### 1. Партнёр: CA и клиентский сертификат бота

Всё выполняется на инфраструктуре партнёра (VPS бота и/или рабочая машина). Закрытый ключ CA и `client.key` оператору API **не передаются**.

Пример (ориентир; партнёр может использовать свой принятый процесс PKI):

```sh
# CA партнёра (один раз)
umask 077
openssl req -x509 -newkey rsa:3072 -nodes -days 365 -keyout ca.key -out ca.crt \
  -subj '/CN=Partner integration CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'

# Клиентский сертификат для бота (партнёр подписывает сам)
openssl req -new -newkey rsa:2048 -nodes -keyout client.key -out client.csr \
  -subj '/CN=misisync-reminder-bot'
printf 'basicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature\nextendedKeyUsage=clientAuth\n' > client.ext
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -days 90 -sha256 -extfile client.ext -out client.crt
```

Оператору API передаётся **только публичный** `ca.crt` (PEM). Им gateway будет проверять клиентские сертификаты, выпущенные этим CA.

Для отладки на второй машине партнёр выпускает **отдельную** клиентскую пару (другой CN), не копируя боевой `client.key`.

Срок клиентских сертификатов и ротация — зона партнёра. Индивидуальный CRL/OCSP на стороне Misisync пока не реализован: экстренный отзыв доступа — замена доверенного `ca.crt` на gateway (новый CA партнёра или согласованный новый якорь) и пересоздание integration-контейнера.

### 2. Оператор: установить CA партнёра на VPS

```sh
mkdir -p /opt/misisync/deploy/integration-pki
# скопировать полученный ca.crt партнёра:
#   /opt/misisync/deploy/integration-pki/ca.crt
chmod 644 /opt/misisync/deploy/integration-pki/ca.crt
```

В репозиторий и git `ca.crt` не коммитится.

### 3. Оператор: секрет канала и включение

```sh
openssl rand -hex 32
```

В серверный `.env`:

```env
INTEGRATION_PROXY_SECRET=<64 hex-символа>
INTEGRATION_ENABLED=true
```

Секрет не передаётся партнёру. В firewall откройте TCP 8443 (при фиксированном IP бота доступ можно ограничить им).

### 4. Оператор: выкладка

Из `/opt/misisync`:

```sh
bash deploy/update.sh <полный_SHA_опубликованного_релиза>
```

Скрипты подключают `compose.integration.yaml`.

### 5. Партнёр: проверка

С хоста бота:

1. без клиентского сертификата — отказ;
2. с чужим / не тем CA — отказ;
3. со своим `client.crt` + `client.key` — ответ расписания.

Доступность порта 443 не гарантирует доступность 8443 — проверяйте отдельно. Серверный сертификат — обычный Let's Encrypt домена; `-k` не нужен.

Продление Let's Encrypt перезагружает оба nginx-gateway. Healthcheck контейнера `integration` проверяет процесс, но не заменяет внешний mTLS-тест. После смены backend-контейнера `update.sh` пересоздаёт `integration`, чтобы обновить DNS Docker-сети.

### 6. Отключение (оператор)

1. Остановить контейнер `integration`.
2. Установить `INTEGRATION_ENABLED=false`, очистить секрет.
3. Выполнить `update.sh`.
4. Закрыть порт 8443.
5. При необходимости удалить `deploy/integration-pki/ca.crt`.

mTLS защищает интеграционный вход; публичные маршруты сайта остаются публичными. Постоянной базы расписания нет: оба API используют общий in-memory кэш и одни правила TTL / stale / отказоустойчивости.

Изменение полей API (деплой новой версии) **не требует** перевыпуска CA или клиентских сертификатов, пока тот же CA остаётся доверенным на gateway. Ломающие изменения контракта сопровождаются обновлением OpenAPI и README.

## Сопровождение контракта

После изменения схемы API обновите OpenAPI из корня репозитория:

```sh
python scripts/export_openapi.py
```

Файл `docs/api/openapi.json` коммитится вместе с кодом.
